## 字段状态

图片观察值使用以下有区别的状态，原文始终保存在 `raw`。原图转录的 `recorded` 意为“图片写明”；采用视图还可来自上节明确的用户决定，须保留对应引用，二者均不表示游戏验证。

| 状态         | 含义与值字段                                                | 原图／历史示例                       |
| ------------ | ----------------------------------------------------------- | ------------------------------------ |
| `recorded`   | 图片可读，结构化值在 `value`。                              | 力气 `"40"` → `40`。                 |
| `tentative`  | 有候选但待确认，仅提供 `candidate` 和原因，不提供 `value`。 | `茄子?`；`水果?`。                   |
| `unknown`    | 完全未知，无 `value` 或 `candidate`。                       | 食材 `?`；旧版力气 `?`。             |
| `not-stated` | 图片没有说明，`raw` 为 `""`。                               | 未提供的特殊效果、食材品质。         |
| `none`       | 有明确“不存在”的证据，必须保留原文和原因。                  | 模型支持；本图没有据此确认的字段。   |
| `unresolved` | 标记存在，但含义不能确认。                                  | 特殊效果 `/`，不自动解释成“无效果”。 |

数据层的空白、`/`、`?` 不互换。页面延续用户要求，将已有配方普通菜的空白和斜杠统一显示为“无特殊效果”；仅列菜名、配方整行留空时效果仍显示“未说明”，但不把原始 `not-stated`／`unresolved` 改成已验证的 `none`；未知和候选仍分开显示。未知力气不填 `0`；真实写明 `0` 时才可以保存数值零。力气必须为非负安全整数且与数字原文相同；不把当前样本的最大值 180 当作游戏上限。字段对象使用严格 schema，未知字段或将 `value` 附加到未知状态都会被拒绝。

## 菜谱解释

- `ingredients` 是有序槽位数组，数量按实际行录入；整行未提供食材时为空数组。重复槽位具有意义，例如两个小麦仍是两项，不转成集合。招牌菜第 33 行有四项；不按分区预设槽位数量。
- 每个槽位的 `selection` 支持 `item`（可辨认的具体食材名）、`category`（如鱼类、颜色水果集合）、`any-of`（同一槽位可选项）。图片没有明确粒度的“鲜花、海鲜、海鱼、淡水鱼、水果”使用 `unspecified`，保留词本身，不断言它是具体游戏道具或已验证类别。`水果类/鲜花` 与 `素食/荤菜` 按同一槽位可选项记录，并保留原文；不由名称展开具体成员。
- `recorded` 食材的结构化名称必须与原文一致；`any-of` 按原文顺序以 `/` 连接各项名称，禁止静默替换或重排，避免页面原文与食材筛选矛盾。此约束不要求候选值包含问号，也不为未知状态添加名称。
- `dishCategory` 单独预留游戏内菜品分类。本图没有独立的分类字段或明确图例，因此全部为 `not-stated`。分区标题、菜名中的“家常／珍稀／梦幻”和底色均不自动写入该字段。
- `ingredients[].quality` 单独表示食材品质要求，有底色的槽位按下节的用户补充规则解释，其余为 `not-stated`。`visualCues` 保留可见的蓝／紫／黄底色和加粗，字段路径 `ingredients.0` 指第一项食材。加粗不作为品质依据，食材名称中的“绿色／黄色”等文字也不代表槽位品质。
- `cookingMethod` 保存“煮锅／榨汁机／烤箱”原文和值；`tags` 保存整格原文和拆开的词条。保留“主菜”等异写，不自动替换为常见词条。
- `specialEffect.value` 拆成名称 `name` 与阶级 `tier`（1、2、3），整格文字仍在 `raw`，校验名称和阶级与原文一致。不同来源的“大力播洒”和“大力播撒”分别保留；当前按小铭新图原文显示“大力播洒”。同一道菜、同一阶级的游戏截图写“大力播洒”，仅在证据关联时按这一异写匹配，不回写原文或改变阶级。
- `effectTrigger` 的 `unspecified-probability` 只承接表头“概率”，`basis` 指向本区效果列表头；不提供数字。`productionChance` 保存自由烹饪效果栏中的“概率出”（`effect-column-cell`）或奇迹盛宴区标题中的“概率产出”（`region-heading`），含义均为菜品产出。校验要求依据与分区相符。它们有不同的字段与来源位置，不能互换；严格 schema 拒绝额外的 `percent` 或 `rate`。
- 明天 9/29 的九条自由烹饪写“概率出”，八条奇迹盛宴由对应词条食物概率产出；没有概率数字，不补猜固定配方。卡拉红汁炖肉为 90 力气、快速翻土二阶；轰炸大菇肉在明天图效果为问号，10/14 写明为 90 力气、煮锅、大力敲伐二阶。

## 来源、注释与核对

每行 `source` 引用来源 ID、分区、行号，借助清点表可回到附件。`noteIds` 引用同一来源的玩家注释。小铭 10/14 备注包括自由烹饪入口、榨汁机与什锦饮限制、谷物与绿色水果说明，以及收录范围（适用全部六区）；9/30 的海鲜类别、问号待测与食材探索备注保存在其来源记录中；明天历史图保留虾类排除螯虾、自由烹饪不在菜谱内显示和竹香苹果冰的友邻解锁条件。全局注释随每行引用，分区限制只挂到适用记录；不把一张图的注释冒充另一张图的原文。校验器拒绝不存在、不适用或遗漏的注释引用。

图片日期只存入 `imageDate`；完整日期使用 ISO 值，仅标月日时保留 `raw`、`value: null` 和必填 `reason`，不借用附件接收年份；`publishedAt`、`gameVersion` 没有资料支撑，保持未说明。原帖 URL 保持未知。所有转录来源和注释都是 `player-record`，所有图片转录记录都是 `image-transcribed-game-unverified`。每版转录只依据对应附件，不混入其他资料或沿用讨论中的数量。甜瓜花茶与满满大烩菜的烹饪方式在明天 9/23 与 9/24 图间不同，分别保存旧记录与新记录，并在新版 `reviewNotes` 中说明，不能宣称其中一个已在游戏中验证。后续[配图来源清单](references/recipes/dish-image-candidates.md)与这里的菜谱来源分别保存。

疑似异写保留当前原文，必要时在 `reviewNotes` 解释。字形不能确认时用 `tentative`；彻底不可读时保留对应行与未知字段，不删除行。`pnpm data:check --details` 会列出候选、未知、未解读标记和核对备注；图片未说明的常规字段不混入这些条目。

## 食材品质要求

2026-09-26 用户补充说明食材单元格底色表示所需品质。解释规则保存在当前来源的 `ingredientQualityInterpretation`，包含稳定 ID、用户原话、确认日期及颜色映射；这是图片之外的用户说明，图片自身的 `visualLegend` 仍为 `not-stated`。

- 有底色的槽位保存 `quality: { status: "interpreted", color, interpretationId }`，紫底为 `purple`、黄底为 `gold`，沿用站内“紫色／金色品质”名称。支持蓝底映射，但当前图中没有蓝底食材格。`interpreted` 表示结合底色与补充规则得出的需求，不伪造图片中的品质文字，也不代表游戏内验证。
- 当前食材底色来自[小铭 10/14 原图](references/recipes/xiaoming-10-14.md)，品质解释引用 `xiaoming-1014-ingredient-background`；若以后有决定按字段采用明天图的整组食材，底色、加粗及解释引用随之切换。历史来源独立保留，不混用颜色槽位。未着色的槽位继续 `not-stated`，不能自动填成普通、蓝色或无品质要求；加粗含义仍未确认。
- 品质附着于有序槽位，重复食材分别保留。例如当前“水果烤虾拼盘”的第二项虾类需紫色品质，第一项未说明；明天历史图标在第一项，不能混用行序。可选关系按整个槽位保留；“茄子?” 的食材候选状态与紫色品质要求各自独立。规则不说明高品质能否替代其他品质。
- 数据集校验会拒绝缺失／跨来源的解释引用、品质颜色与底色不符、无底色却添加解释、同槽位底色冲突，以及有底色却遗漏品质。9 月 23 日历史快照保持原字节，不追溯改写其字段。

页面的所需食材同时显示底色和“需紫色／金色品质”等文字。用户规则与原图位置保留在本地资料中；菜品品质及效果阶级不受此字段影响。

## 维护与验证

从原图复核清点表后再改转录记录，常规更正不改变行号与 ID。修改行数、来源或引用时一并复核独立清点表，不能为了让检查通过而用当前数组长度替代预期数量。变更来源图片必须更新来源记录并说明原因；哈希变化会使检查失败。

`pnpm data:check` 已接入 `pnpm check`，检查严格字段类型、枚举、数字范围、重复 ID、来源／行号／注释引用、原图定位、完整覆盖率、历史引用、附件完整性、独立菜品品质和食材品质解释。Vitest 以真实记录覆盖重复槽位、可变食材数量、未知值、异写、视觉语义和概率语义。命令与运行环境见[开发指南](development.md)。这些检查确认数据一致性与转录约束，不构成游戏内验证。
