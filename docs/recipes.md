# 菜谱数据约定

本轮只处理用户提供的明天攻略组《星布谷地菜谱图鉴》图片，图片标注日期为 2026-09-23。数据用于后续烹饪速查页面，目前没有页面、接口或发布变更。覆盖情况和未决事项见[转录报告](references/recipes/tomorrow-2026-09-23.md)。

## 文件与读取边界

| 文件                                                         | 职责                                                                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `data/recipes/recipes.json`                                  | 菜谱原文、结构化解释、视觉线索和逐行来源引用；菜谱事实的维护入口。                                           |
| `data/recipes/sources.json`                                  | 来源、制作者、图片日期、文件信息及玩家注释的权威记录。                                                       |
| `docs/references/recipes/tomorrow-2026-09-23.png`            | 未改动的原尺寸附件，不放进站点 `public/`。                                                                   |
| `docs/references/recipes/tomorrow-2026-09-23.inventory.json` | 先于完整转录建立的独立清点表，包含分区、行号、菜名辨读、表头与原图像素定位。不能从菜谱数组重新生成预期数量。 |
| `shared/recipes/schema.ts`                                   | Zod schema、跨记录约束与通过 `z.infer` 推导的 TypeScript 类型。                                              |
| `shared/recipes/index.ts`                                    | JSON 读取时立即校验的共用入口，导出 `recipeDataset`。消费方不直接断言原始 JSON 类型。                        |
| `shared/recipes/review.ts`                                   | 从记录状态和核对备注汇总待核对字段，保留来源分区与行号。                                                     |
| `scripts/check-recipes.ts`                                   | 本地数据校验入口，另检查附件文件、SHA-256、大小与 PNG 尺寸。                                                 |

稳定来源 ID 为 `tomorrow-20260923-image`。菜谱 ID 采用 `mt-20260923-<region>-<三位行号>`，标识本张图片的一条记录，不宣称是游戏官方 ID。更正辨读文字时保留 ID；另一张图片使用另一来源 ID，不能覆盖本图原文。

`source.region` 只表示图片位置：`simple` 简单菜、`signature` 招牌菜、`guest` 宴客菜、`free` 自由烹饪、`neighbor` 友邻秘方。行号在各区自上而下从 1 开始，只计有内容的数据行，不计表头、空白网格或署名。定位矩形是原图左上角为原点的 `[x, y, width, height]`，用于定位整行而非精确分割文字；招牌菜第 33 行的矩形包括向右扩展部分。

## 字段状态

图片观察值使用以下有区别的状态，原文始终保存在 `raw`。`recorded` 意为“图片写明”，不表示游戏验证。

| 状态         | 含义与值字段                                                | 本图示例                             |
| ------------ | ----------------------------------------------------------- | ------------------------------------ |
| `recorded`   | 图片可读，结构化值在 `value`。                              | 力气 `"40"` → `40`。                 |
| `tentative`  | 有候选但待确认，仅提供 `candidate` 和原因，不提供 `value`。 | `茄子?`；菜名第四字暂读作“笃”。      |
| `unknown`    | 完全未知，无 `value` 或 `candidate`。                       | 食材 `?`、力气 `?`。                 |
| `not-stated` | 图片没有说明，`raw` 为 `""`。                               | 自由烹饪效果空白、食材品质。         |
| `none`       | 有明确“不存在”的证据，必须保留原文和原因。                  | 模型支持；本图没有据此确认的字段。   |
| `unresolved` | 标记存在，但含义不能确认。                                  | 特殊效果 `/`，不自动解释成“无效果”。 |

空白、`/`、`?` 不互换。未知力气不填 `0`；真实写明 `0` 时才可以保存数值零。力气必须为非负安全整数且与数字原文相同；不把当前样本的最大值 180 当作游戏上限。字段对象使用严格 schema，未知字段或将 `value` 附加到未知状态都会被拒绝。

## 菜谱解释

- `ingredients` 是有序槽位数组，数量按实际行录入。重复槽位具有意义，例如两个小麦仍是两项，不转成集合。招牌菜第 33 行有四项；不按分区预设槽位数量。
- 每个槽位的 `selection` 支持 `item`（可辨认的具体食材名）、`category`（如鱼类、颜色水果集合）、`any-of`（同一槽位可选项）。图片没有明确粒度的“鲜花、海鲜、海鱼、淡水鱼、水果”使用 `unspecified`，保留词本身，不断言它是具体游戏道具或已验证类别。`水果类/鲜花` 与 `素食/荤菜` 按同一槽位可选项记录，并保留原文；不由名称展开具体成员。
- `dishCategory` 单独预留游戏内菜品分类。本图没有独立的分类字段或明确图例，因此全部为 `not-stated`。分区标题、菜名中的“家常／珍稀／梦幻”和底色均不自动写入该字段。
- `ingredients[].quality` 单独表示食材品质，本图全部为 `not-stated`。`visualCues` 仅记录可见的蓝／紫／黄底色和加粗，字段路径 `ingredients.0` 指第一项食材。没有线索项表示本轮未记录特殊样式，不表示已确认某种品质。颜色与加粗的含义待核对。
- `cookingMethod` 保存“煮锅／榨汁机／烤箱”原文和值；`tags` 保存整格原文和拆开的词条。保留“主菜”等异写，不自动替换为常见词条。
- `specialEffect.value` 拆成名称 `name` 与阶级 `tier`（1、2、3），整格文字仍在 `raw`，校验名称和阶级与原文一致。“大力播洒”和“大力播撒”分别保留，是否同一效果未定。
- `effectTrigger` 的 `unspecified-probability` 只承接表头“概率”，`basis` 指向本区效果列表头；不提供数字。`productionChance` 则保存自由烹饪效果栏中的“概率出”，其含义是菜品产出。它们有不同的字段与来源位置，不能互换；严格 schema 拒绝额外的 `percent` 或 `rate`。
- 自由烹饪饮品第 5、6 行只对力气写了问号，效果栏是空白，不补“概率出”。自由烹饪有四行明确写“概率出”。

## 来源、注释与核对

每行 `source` 引用来源 ID、分区、行号，借助清点表可回到附件。`noteIds` 引用同一来源的玩家注释：虾类不包含螯虾、自由烹饪不在菜谱内显示、友邻秘方需要获赠并解锁后才能制作。全局注释随每行引用；分区限制只挂到对应记录。校验器会拒绝不存在、不适用或遗漏的注释引用。

图片日期只存入 `imageDate`；`publishedAt`、`gameVersion` 没有资料支撑，保持未说明。原帖 URL 保持未知。所有来源和注释都是 `player-record`，所有记录都是 `image-transcribed-game-unverified`。本轮不引入其他版本或资料，不复用之前讨论的数量；未来若有矛盾资料，应另存来源及其记录，不能覆盖本图或宣称其中一个已验证。

疑似异写保留当前原文，必要时在 `reviewNotes` 解释。字形不能确认时用 `tentative`；彻底不可读时保留对应行与未知字段，不删除行。`pnpm data:check --details` 会列出候选、未知、未解读标记和核对备注；图片未说明的常规字段不混入这些条目。

## 维护与验证

从原图复核清点表后再改转录记录，常规更正不改变行号与 ID。修改行数、来源或引用时一并复核独立清点表，不能为了让检查通过而用当前数组长度替代预期数量。变更来源图片必须更新来源记录并说明原因；哈希变化会使检查失败。

`pnpm data:check` 已接入 `pnpm check`，检查严格字段类型、枚举、数字范围、重复 ID、来源／行号／注释引用、原图定位、完整覆盖率与附件完整性。Vitest 以真实记录覆盖重复槽位、可变食材数量、未知值、异写、视觉语义和概率语义。命令与运行环境见[开发指南](development.md)。这些检查确认数据一致性与转录约束，不构成游戏内验证。
